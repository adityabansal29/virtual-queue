    type AdmissionClaims struct {

        TicketID string `json:"ticketId"`

    Define `ValidateJWT(tokenString, secret string) (*AdmissionClaims, error)`:
    - Parse with `jwt.ParseWithClaims(tokenString, &AdmissionClaims{}, func(t *jwt.Token) (interface{}, error) { if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok { return nil, fmt.Errorf("unexpected signing method") }; return []byte(secret), nil })`
    - Return claims if valid, error otherwise (covers wrong secret, expired, malformed)

    Define `Config` struct for middleware (separate from internal/config.Config to keep pkg/ decoupled from internal/):
    ```
    type Config struct {
        AdmissionSecret string
        SessionSecret   string
        QueueURL        string
        RDB             *redis.Client
    }
    ```

    Define `QueueGuard(cfg Config) gin.HandlerFunc` implementing the flow from DESIGN.md Section 8 exactly:
    1. Session cookie fast path: `c.Cookie("q_session")`. If found, call `token.ValidateSession(sc, cfg.SessionSecret)`. If nil error → `c.Next(); return`.
    2. Admission token check: `c.Cookie("q_admission")`. If not found → redirect to `cfg.QueueURL+"?target="+url.QueryEscape(c.Request.URL.String())`, `c.Abort()`, return.
    3. `claims, err := token.ValidateJWT(ac, cfg.AdmissionSecret)`. If err → redirect same as step 2, `c.Abort()`, return.
    4. SETNX: `set, err := cfg.RDB.SetNX(c.Request.Context(), "token:"+claims.ID, "used", 30*time.Minute).Result()`. If err != nil OR !set → `c.AbortWithStatus(http.StatusForbidden)`. Return. (TOKEN-04: SETNX atomicity guarantees exactly-once — if two identical JWTs arrive simultaneously, Redis SETNX is atomic: exactly one Set call returns true, the other returns false.)
    5. Increment active: `cfg.RDB.Incr(c.Request.Context(), "active:"+claims.EventID)`. (TOKEN-05)
    6. Issue session cookie: `sc, _ := token.IssueSession(claims.Subject, claims.EventID, cfg.SessionSecret)`. `c.SetCookie("q_session", sc, 1800, "/", "", true, true)`.
    7. Clear admission cookie: `c.SetCookie("q_admission", "", -1, "/", "", true, true)`. (TOKEN-06)
    8. `c.Next()`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser cookie → QueueGuard | q_admission JWT arrives from untrusted browser; must be HMAC-verified before trusting claims |
| QueueGuard → redis-origin | SETNX call on redis-origin — internal Docker network; no auth in Phase 1 |
| scheduler → queueserver → browser | JWT delivered via SSE/poll; HMAC-signed with ADMISSION_SECRET |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Spoofing | q_admission cookie — forged JWT | high | mitigate | ValidateJWT rejects any token not signed with ADMISSION_SECRET. golang-jwt validates signature before returning claims. Malformed or forged tokens receive redirect to queue join. |
| T-03-02 | Tampering | token:{jti} SETNX — replay attack | high | mitigate | SETNX is atomic. Even if two goroutines present the same JWT simultaneously, exactly one SetNX succeeds (TOKEN-04 backstop). Second call returns !set → 403. |
| T-03-03 | Information Disclosure | ADMISSION_SECRET and SESSION_SECRET in env vars | high | mitigate | Secrets never logged (no slog fields containing secret values). .env in .gitignore. config.Load() panics on empty or identical secrets. Two independent secrets — compromise of one does not expose the other (TOKEN-02). |
| T-03-04 | Elevation of Privilege | Session cookie signed with SESSION_SECRET used to bypass QueueGuard | medium | mitigate | ValidateSession uses SESSION_SECRET; ValidateJWT uses ADMISSION_SECRET. A q_session token presented as q_admission will fail signature verification (different key). Two-secret isolation tested by TestSessionSecretIsolation. |
| T-03-05 | Tampering | q_session cookie forgery | high | mitigate | Issued by QueueGuard with Secure+HttpOnly flags. Signed with SESSION_SECRET. EdgeWorker (Phase 3) will verify inline. Phase 1: QueueGuard fast-path verifies on every request to stub origin. |
| T-03-06 | Denial of Service | token:{jti} key flood — attacker generates many valid JWTs | medium | accept | Each JTI requires a prior valid q_admission JWT from the scheduler — which requires a valid ticketId that was actually popped from the queue. No forged JWTs possible without ADMISSION_SECRET. |
| T-03-SC | Tampering | golang-jwt package supply chain | high | mitigate | golang-jwt/jwt/v5 verified at pkg.go.dev. go.sum content-addressable integrity. Well-known library (successor to dgrijalva/jwt-go per pkg.go.dev docs). |
</threat_model>
